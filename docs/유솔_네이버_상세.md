# 유솔 네이버 정산 상세 (참고 자료)

**작성일**: 2026-04-30 EOD
**용도**: Phase 1 = 수동 입력 가이드 / Phase 2 = 자동 import 시 매핑 참고
**관련**: `정산_운영_매뉴얼.md`, `Phase1_MVP_계획.md`, `그릇_아키텍처.md`

## 자금 흐름

```
고객 결제
  ↓ (네이버 스마트스토어, 유솔 명의)
네이버페이
  ↓ (네이버 수수료 차감)
유솔 통장
  ↓ 매주 월요일
사장님 통장
  ↓
기사 통장
```

**핵심**:
- 네이버 스마트스토어 = **유솔 명의**
- 유솔이 시트 export → 사장님에게 전달 → 사장님이 운영 시스템에 입력
- 자동 동기화 X (Phase 1)

---

## 네이버 시트 컬럼 (export 형식 그대로)

미래 자동 import 시 매핑표:

| 네이버 컬럼 | 의미 | DB 매핑 |
|---|---|---|
| 상품주문번호 | 네이버 주문 ID | `tasks.category_data.naver_order_no` |
| 옵션정보 | "1way / 실외기 / 송풍팬분해" 등 | `task_items` 분리 |
| 수량 | qty | `task_items.qty` |
| 옵션가격 / 상품가격 | 단가 | `task_items.unit_price` |
| 최종 상품별 총 주문금액 | 고객 결제액 | `total_amount` 검증용 |
| 네이버페이 주문관리 수수료 | 약 2.56% | `payments.naver_fee` |
| 매출연동 수수료 | 1.0~3.0% 변동 | `payments.naver_fee` 합산 |
| 정산예정금액 | 유솔이 받는 금액 | (단가 − naver_fee) — 분배 base |

---

## 한 주문에 여러 상품 케이스 ✅

발견 사례:
- 같은 주문번호에 **1way 3대 + 스탠드 1대**
- 옵션(실외기 / 송풍팬분해) **별도 정산** 케이스

**검증 결과**: `task_items` 모델로 표현 가능 ✅
- 한 `tasks` row 안에 `task_items` 여러 줄
- 각 라인이 자기 `work_type` + `appliance_type` + `qty` + `unit_price`
- `compute_payment` 라인별 정책 룩업 + 합산 (Phase 2 자동화 시)

## 정산 타이밍 표

| 원청 | 타이밍 | 비고 |
|---|---|---|
| 올데이케어 (O) | 당일 | 자체 영업 |
| 쿨가이 (K) | 당일 | 직영 |
| 용인컴퍼니 (Y) | 당일 | 직영 |
| 유솔 현금 (H) | 당일 | 유솔이 현금 받음 |
| **유솔 네이버 (N)** | **매주 월요일** | 유솔 → 사장님 → 기사 |

`payments.expected_settlement_date`:
- H/O/K/Y: 작업일 = 정산일
- N: 작업일이 속한 주 다음 월요일

## Phase 1 처리 = 수동 입력

- 사장님/해피콜이 유솔 시트 보고 PWA 직접 입력
- `payments.naver_fee` 컬럼: 네이버 수수료 합계 직접 입력
- `compute_payment` 함수는 그대로 (자동 분기 X)
- 검증: `payments.is_balanced` — `(단가 × 수량) − naver_fee` 가 분배 합과 일치하는지 확인
- `expected_settlement_date` 도 수동 입력 (작업일 기준 다음 월요일 자동 추천 UI 가능)

---

## Phase 2 자동화 (운영 1-2주 후 검토)

조건: 운영 데이터 1-2주 쌓이면 → 패턴 정확화 → 자동화

작업:
- 네이버 시트 import 도구 (사장님 업로드 또는 Edge Function)
- `compute_payment` 함수 시그니처에 `p_naver_fee` 추가 + 'N' 분기:
  ```
  IF principal_code = 'N' THEN
    base_amount := p_unit_price - p_naver_fee
  ELSE
    base_amount := p_unit_price
  END IF
  ```
- `정산예정금액` 자동 검증 (시트 vs DB)

## settlement_status 흐름 (한글 enum)

```
대기 → 진행중 → 완료
              ↓
        지연 / 분쟁
```

| 상태 | 의미 |
|---|---|
| 대기 | 작업 완료, 정산 시작 전 |
| 진행중 | 유솔 → 사장님 입금 대기 (네이버 케이스) / 사장님 → 기사 송금 대기 |
| 완료 | 사장님 → 기사 입금 끝 |
| 지연 | `expected_settlement_date` 지났는데 입금 안 됨 (15일+) |
| 분쟁 | `task_disputes` 열린 상태 |
