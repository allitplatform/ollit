# 정산 운영 매뉴얼 — 8가지 계산방식 + 분배 철학

**작성일**: 2026-04-30
**대상**: 운영 신규 입사자 / 사장님 본인 / 시스템 점검 시 참고
**상태**: ✅ 14개 결정 답변 반영, 8 calc_method 확정

---

## 정산의 세 축

### 1. 정보 비대칭 — 사장님 마진의 원천 ★

```
기사기준금  =  원청에게 알려진 기사 수익 (표면)
기사AD     =  실제 기사 받는 금액 (이면)
차이       =  사장님 자동 마진
```

DB는 두 값 모두 저장. 원청(partner)은 둘 다 안 봄. 기사도 자기 AD만. 사장님만 가시.

### 2. 카테고리별 분배 철학

| 작업 종류 | 누가 노력? | 분배 |
|---|---|---|
| 메인 작업 (에어컨 청소 등) | 사장님 영업/관리 | 사장님이 마진 확보 |
| 옵션 (송풍팬, 실외기, 피톤치드…) | 기사 현장 영업 | **기사 85% / 원청 15% / 사장님 0** |
| 출장비 (작업 불가 시) | 기사 출장만 | **기사 100%** |
| 현장 추가금 (메인 외 추가) | 사장님 + 기사 | **50/50** (예상금액비율 카테고리는 원청 0%) |

### 3. 수량은 모든 정책의 기본 차원 ★

모든 calc_method에서 수량 곱은 자동. 단가 한 대당 분배 → × `qty`.
예외: `비율_총액기준` 만 합계 기준이라 수량 곱 SKIP.

## 8가지 계산방식 — 풀이 + 예시

### A. 차감후비율 (쿨가이 에어컨 세척)

```
한 대당 분배:
  기사   = 기사AD
  원청   = (단가 - 기사기준금) × 50%
  사장님 = (기사기준금 - 기사AD) + (단가 - 기사기준금) × 50%   ← 정보차익 + 영업차익
× 수량
```

**예** (단가 70,000 / 기준금 50,000 / AD 40,000 / 1대):
- 기사 40,000 / 쿨가이 10,000 / 사장님 20,000 = 70,000 ✓

**예** (3대 — 수량 자동):
- 기사 120,000 / 쿨가이 30,000 / 사장님 60,000 = 210,000 ✓

---

### B. 비율 (유솔 네이버, 일반)

```
한 대당:
  기사   = 기사AD
  원청   = 단가 × 비율 (보통 15%)
  사장님 = 단가 - 기사 - 원청
× 수량
```

**예** (유솔 네이버 벽걸이 2대, 단가 68,000 / AD 44,000):
- 기사 88,000 / 유솔 20,400 / 사장님 27,600 = 136,000 ✓

---

### C. 금액 (용인, 올데이케어)

```
한 대당:
  기사   = 기사AD
  원청   = 정액
  사장님 = 단가 - 기사 - 원청
× 수량
```

**예 1** (용인 2대, 단가 50,000 / 정액 10,000):
- 기사 80,000 / 용인 20,000 / 사장님 0 *(이 단가 마진 없음 → 더 비싸게)*

**예 2** (올데이케어 5대 자체영업, 단가 40,000 / AD 40,000 / 정액 0):
- 기사 200,000 / 올데이 0 / 사장님 0 *(단가 더 받아야 마진)*

---

### D. 수량비율 (시트 호환)

`비율`과 동일 처리. 모든 case가 수량 곱이라 별도 의미 없지만 시트 호환을 위해 enum 유지.

---

### E. AG전체_AD반반 (유솔 추가선택 — 냉매점검 등) ★ 한 정책 3 케이스

| 케이스 | 분배 |
|---|---|
| 기본 작업 (네이버 결제 1만) | 유솔 100%, 기사 0, 사장님 0 |
| 현장 추가 발생 시 (예: 5,000) | 추가분 = 사장님 50% + 기사 50% (유솔은 기본분만) |
| 출장비 (작업 불가, 30,000) | 기사 100% |

→ 한 정책이 product/extra/travel 입력을 다르게 분배.

---

### F. 예상금액비율 (쿨가이 가스) ★ KA/KB 분리

```
한 대당:
  원청   = 견적 × principal_fee%   (정책 행 기반 — 동적)
  기사   = 견적 × 50%
  사장님 = 견적 - 기사 - 원청
× 수량
```

| 쿨가이 | principal_fee | 분배 (한 대당, 견적 100,000 가정) |
|---|---|---|
| **KA (아버지)** | **10%** | 원청 10,000 / 기사 50,000 / 사장님 40,000 |
| **KB (아들)** | **35%** | 원청 35,000 / 기사 50,000 / 사장님 15,000 |

KA가 사장님 마진이 큰 이유: 영업 노력 + 정보 비대칭 더 큼. KB는 표준에 가까움.

**현장 추가금 발생 시**: 추가금은 **쿨가이 0%** (제외) → 사장님/기사 50/50 추가.

---

### G. 비율_총액기준 (쿨가이 가스 — 1way/4way/원형 2개+) ★ 신규

```
기준 금액 = (단가 × 수량) + 추가금   ← 추가금 포함 합계
  쿨가이 = 기준 × 25%
  기사   = 기준 × 50%
  사장님 = 기준 × 25%
```

**예** (1way 2대, 단가 100,000 + 추가 50,000):
- 기준 = 100,000 × 2 + 50,000 = 250,000
- 쿨가이 62,500 / 기사 125,000 / 사장님 62,500 = 250,000 ✓

→ 수량과 추가금이 이미 합계에 포함, 별도 분배 X.

---

### H. 추가선택 (유솔 송풍팬 / 실외기 / 피톤치드 등)

```
한 대당:
  기사   = 단가 × 0.85
  원청   = 단가 × 0.15
  사장님 = 0
× 수량
```

**왜 사장님 0?** 이 옵션은 기사가 현장에서 직접 영업 = 기사 동기 부여. 사장님은 메인 작업에서 마진 확보, 옵션은 기사 몫.

## 출장비 / 현장 추가금 룰 정리

### 출장비 (`travel_fee`) — 수량 무관, 한 번 발생
- **언제**: 기사가 현장 갔는데 작업 불가 (고객 부재 등)
- **금액**: 30,000원 (표준)
- **분배**: 기사 100% / 원청 0 / 사장님 0

### 현장 추가금 (`extra_fee` + `extra_reason`) — 수량 무관, 한 번
| 정책 | 분배 |
|---|---|
| 일반 (대부분) | 사장님 50% + 기사 50% |
| 예상금액비율 (쿨가이 가스) | **원청 0%**, 사장님 50% + 기사 50% |
| 비율_총액기준 | 추가금이 이미 합계에 포함 → 별도 분배 X |

## 유솔 정산 타이밍 (Day 0 추가)

### 자금 흐름

```
고객 결제
  ↓ (네이버 = 유솔 명의 스마트스토어, 현금 = 유솔 직수령)
유솔 통장
  ↓ (유솔 수수료 차감 후)
사장님 통장
  ↓
기사 통장
```

유솔이 **중간 정산** 역할. 사장님은 시트(유솔 export) 받아서 운영.

### 현금 (H) vs 네이버 (N) 차이

| 항목 | 현금 (H) | 네이버 (N) |
|---|---|---|
| 단가 | 비슷 (시트 분리는 형식적) | 비슷 |
| **정산 기준** | 단가 전체 | **단가 − 네이버수수료** (이미 차감된 base에서 분배) |
| **정산 타이밍** | 당일 (직영과 같이) | **매주 월요일** (작업일 + 최대 15일+) |

### 원청별 정산 일정

| 원청 | 타이밍 |
|---|---|
| 올데이케어 (O) / 쿨가이 (K) / 용인 (Y) / 유솔 현금 (H) | 당일 |
| **유솔 네이버 (N)** | **작업일이 속한 주의 다음 월요일** |

### settlement_status 흐름

```
대기 → 진행중 → 완료
              ↓
        지연 / 분쟁
```

| 상태 | 의미 |
|---|---|
| 대기 | 작업 완료, 정산 시작 전 |
| 진행중 | 유솔→사장님 또는 사장님→기사 송금 중 |
| 완료 | 입금 다 끝남, `actual_settlement_date` 채워짐 |
| 지연 | `expected_settlement_date` 지났는데 미입금 (15일+) |
| 분쟁 | `task_disputes` 열림 |

### Phase 1 = 수동 입력

- 사장님/해피콜이 유솔 시트 보고 PWA 직접 입력
- `payments.naver_fee` 칸에 네이버 수수료 합계 직접 (Phase 1은 분배에 영향 X, 메타정보 보존)
- `expected_settlement_date` 도 직접 입력 (네이버 = 다음 월요일 자동 추천 UI 가능)
- 자세한 Phase 2 자동화 가이드 → `유솔_네이버_상세.md`

## 케이스별 Q&A

**Q. 정책 없는 작업 (예: 신규 원청)**
→ PWA "정책 없음 — 수동 입력 모드" 전환. owner가 분배 직접 입력. Phase 2에서 빈도 보고 정책 추가.

**Q. 분배 합계가 안 맞으면?**
→ `payments.is_balanced = false` 자동. owner 화면 빨간 알림. 정책/입력값 점검 → 재계산.

**Q. partner가 정산 항의 (수치 다름)**
→ `task_disputes` 열림. partner가 메시지 → owner 응답. 정책 시트가 진실. partner는 자기 `principal_amount`만 봄.

**Q. 기사가 자기 AD 다르다고 하면?**
→ `engineer_actual_ad` 정책 시트 확인. 시트가 진실. 수정은 시트 → DB import.

**Q. 월별 일괄 정산?**
→ `payments.status='confirmed'` 인 것 → 매월 말 owner UI 일괄 `status='paid'` + `settled_at` 채움.

## 분배 검증 (`is_balanced` 자동)

```
engineer + principal + owner  ===  product_total + extra_fee + travel_fee
                                   (product_total = unit_price × qty)
```

이 등식이 안 맞으면 DB가 자동 `false` → 빨간 알림. 신뢰성 마지막 방어선.

## 정산 워크플로 (지급 흐름) ★ v3 (Phase 1 v5.1)

### 기사 정산 — 양방향 확인 (4단계)

`payments.status` enum:

```
미정산
  ↓ 사장님 [입금 완료] 클릭 (D 화면)
사장님입금        (paid_at = now)
  ↓ 기사가 본인 화면 (F)에서 [입금 확인] 클릭
기사확인          (confirmed_at = now)
  ↓ 사장님이 [정산 완료] 클릭 (D 화면)
정산완료          (settled_at = now)
```

**예외 status**:
- `보류` — 사장님이 일시 보류 (예: 작업 미완성)
- `분쟁` — 기사 항의 또는 검증 실패 (`task_disputes` 자동 연동)
- `지연` — `expected_settlement_date` 지났는데 미입금

**왜 양방향?**: 입금 사고 (오송금/누락) 추적. 기사 [입금 확인]이 영수증 역할.

### 원청 정산 — 한 클릭 (단방향)

원청은 본인 화면에서 [입금 확인] 안 함 (외부 거래처 — 별도 흐름). 사장님이 [입금 완료] 클릭 → **자동 `정산완료`** (paid_at + settled_at 동시 채움).

| 원청 | 흐름 | 비고 |
|---|---|---|
| KA / KB / 세스코 | 사장님 한 클릭 → 자동 정산완료 | confirmed_at = NULL |
| 유솔 H/N | **Phase 2 예정** — Phase 1 MVP에선 작업 데이터만 동기화, 정산 자동 X | `유솔_네이버_상세.md` 참조 |
| 올데이케어 (O) | 정산 화면 노출 X (직영, 자체 영업) | `principal_amount = 0` |

### Phase 2 미루기 (정산 자동화)

- 유솔 네이버 결제 정산 (네이버 → 유솔 → 사장님 자금 흐름 자동화)
- 정산 이력 통계/리포트 (월별, 기사별, 원청별 trend)
- 분쟁 처리 자동화 (예: 분배 합 불일치 시 자동 분쟁 row 생성)
