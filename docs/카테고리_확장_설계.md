## 핵심 질문

> **새 카테고리(도어락)를 추가할 때 코드 변경은 어디까지인가?**

**이상**: 데이터(설정) 추가만, 코드 변경 0
**현실**: 90% 데이터 / 10% UI 분기

이 문서는 그 분기를 **어떻게 최소화하고**, 분기가 필요한 곳을 **어디에 박아둘지** 설계.

## 카테고리란

올잇이 다루는 **홈서비스 한 영역**. 각 카테고리는 다음 5가지가 다를 수 있음:

| 차이점 | 예시 |
|---|---|
| 1. **단위** | 에어컨 "대" vs 대리석 "㎡" vs 청소 "시간" |
| 2. **가격 모델** | 단가표 vs 면적×단가 vs 정액 vs 출장비별도 |
| 3. **기사 자격** | 냉매 자격증 / 시공 기능사 / 잠금장치 / 없음 |
| 4. **사진 요구사항** | before/after 2단계 vs 시공 전/중/후 3단계 |
| 5. **폼 특이 필드** | 가전종류+수량 / 면적+옵션 / 모델명 / 도어종류 |

이 5가지가 같으면 코드 분기 없이 정형 처리 가능.

## 3가지 카테고리 예시 설계

### 카테고리 1 — 에어컨 (현재 진행 중)

**메타**:
```json
{
  "code": "aircon",
  "name": "에어컨",
  "unit": "대",
  "qty_kind": "integer"
}
```

**서비스 종류 (service_types)**:
| code | 이름 |
|---|---|
| clean | 청소 |
| install | 설치 |
| remove | 철거 |
| relocate | 이전 |
| recharge | 냉매충전 |
| inspect | 점검 |
| repair | 수리 |

**기종 (appliance_types)**:
| code | 이름 |
|---|---|
| wall | 벽걸이 |
| stand | 스탠드 |
| system | 시스템 |
| ceiling | 천장형 |
| multi | 멀티 |
| window | 창문형 |

**작업 종류 (work_types) = 서비스 × 기종 단가표** (예시):

| 서비스 | 기종 | 기본 단가(원) |
|---|---|---|
| clean | wall | 50,000 |
| clean | stand | 80,000 |
| clean | system | 120,000 |
| install | wall | 100,000 |
| install | system | 250,000 |
| recharge | (무관) | 80,000 |
| inspect | (무관) | 30,000 |

**기사 자격**:
- 냉매충전 → 냉매 자격증 보유 기사만 배정 가능
- 다른 작업 → 일반 가전 기사 OK

**사진 단계**: `["before", "after"]`

**폼 특이**: 가전 종류 (다중 선택) + 각 수량 → task_items 여러 줄

---

### 카테고리 2 — 청소기 (가상 설계)

**메타**:
```json
{
  "code": "vacuum",
  "name": "청소기",
  "unit": "대",
  "qty_kind": "integer"
}
```

**서비스 종류**:
| code | 이름 |
|---|---|
| clean | 청소 (분해 청소) |
| filter | 필터교체 |
| repair | 수리 |
| maintain | 정기관리 |

**기종**:
| code | 이름 |
|---|---|
| wired | 일반(유선) |
| stick | 무선 스탠드 |
| handy | 핸디형 |
| robot | 로봇청소기 |

**작업 종류** (예시):
| 서비스 | 기종 | 단가 |
|---|---|---|
| clean | stick | 40,000 |
| clean | robot | 60,000 |
| filter | (무관) | 15,000 + 부품비 |

**기사 자격**: 가전 일반 (특수 자격 없음)

**사진 단계**: `["before", "after"]`

**폼 특이**:
- **모델명 입력 필드 추가** (호환 부품 확인용) ← 카테고리별 추가 필드
- → `tasks.category_data.model_name` JSONB로 저장

---

### 카테고리 3 — 대리석 (가상 설계)

**메타**:
```json
{
  "code": "marble",
  "name": "대리석",
  "unit": "㎡",
  "qty_kind": "decimal"
}
```

**서비스 종류**:
| code | 이름 |
|---|---|
| install | 시공 |
| polish | 광택 |
| repair | 보수 |
| maintain | 정기관리 |

**기종** (선택적 — 대리석은 종류라기보다 면적 중심):
| code | 이름 |
|---|---|
| natural | 천연 대리석 |
| engineered | 인조 대리석 |

**작업 종류** (예시):
| 서비스 | 기종 | 단가 (원/㎡) |
|---|---|---|
| install | natural | 200,000 |
| install | engineered | 80,000 |
| polish | (무관) | 30,000 |

**기사 자격**: 시공 기능사 자격증

**사진 단계**: `["전", "중", "후"]` (3단계)

**폼 특이**:
- **면적(㎡) 입력** — 정수가 아닌 소수점 (12.5㎡)
- **공간 종류 선택** (주방/욕실/거실) ← `category_data.room_type`
- **옵션 (모서리 처리, 광택 등급)** ← `category_data.options`

---

## 차이를 어디서 흡수하는가

### 차이 1 — 단위 / 수량 종류 (정수 vs 실수)

| 카테고리 | 단위 | qty 입력 |
|---|---|---|
| 에어컨 | 대 | 정수 |
| 청소기 | 대 | 정수 |
| 대리석 | ㎡ | 실수 |

**해결**:
- DB: `task_items.qty NUMERIC` (정수도 실수도 OK)
- 카테고리 메타: `categories.qty_kind` ('integer' | 'decimal')
- UI: 입력 컴포넌트가 `qty_kind` 보고 type=number step=1 또는 step=0.1

→ 데이터 + 1 분기 (UI 컴포넌트의 step 속성)

### 차이 2 — 가격 모델

| 카테고리 | 모델 | 계산 |
|---|---|---|
| 에어컨 | 단가표 | unit_price × qty |
| 청소기 | 단가표 + 부품비 | unit_price × qty + parts_cost |
| 대리석 | 면적×단가 | unit_price × area + options |
| 도어락 | 정액 + 출장비 | flat_price + travel_fee |

**해결**:
- `categories.config.pricing_kind`: `'unit_price_table'` | `'area_x_rate'` | `'flat'`
- pricing_rules.config JSONB: 모델별 다른 schema 흡수
  ```json
  // 단가표
  { "kind": "unit_price_table" }
  // 면적
  { "kind": "area_x_rate", "options": { "edge_finish": 20000 } }
  // 정액
  { "kind": "flat", "travel_fee": 30000 }
  ```
- 견적 계산 함수 `computeEstimate(category, items, options)` 가 `pricing_kind` 보고 분기

→ 데이터 + 1 함수 분기 (회계 로직)

### 차이 3 — 기사 자격

**해결**:
- `engineer_categories` (기사 ↔ 카테고리 M:N) — 기사가 처리 가능한 카테고리만
- 일부 work_type은 추가 자격 필요: `work_types.required_cert` (text, NULL이면 없음)
- 배정 UI에서 자동 필터: 자격 없는 기사는 회색

→ 데이터만, 코드 변경 0

### 차이 4 — 사진 단계

| 카테고리 | 단계 |
|---|---|
| 에어컨 | ['before', 'after'] |
| 청소기 | ['before', 'after'] |
| 대리석 | ['전', '중', '후'] |
| 도어락 | ['after'] (설치 후만) |

**해결**:
- `categories.config.photo_steps`: 배열
- 사진 화면이 `photo_steps`만큼 슬롯 표시
- 업로드 시 `photos.step` 값 = 슬롯 라벨

→ 데이터만, 코드 변경 0

### 차이 5 — 폼 특이 필드 (가장 까다로움)

청소기 모델명, 대리석 면적, 도어락 도어종류 등 **카테고리에만 있는 필드**.

**3단계 흡수 전략**:

#### 5-1. 공통 필드 (모든 카테고리) — 정형 컬럼
- 고객명, 전화, 주소, 요청날짜, 요청시간, 요청사항, 카테고리, 채널 …
- → `tasks` 테이블 정형 컬럼

#### 5-2. 카테고리별 필드 (소수) — JSONB
- 청소기 모델명, 대리석 면적, 도어락 도어종류 …
- → `tasks.category_data` JSONB

#### 5-3. 카테고리별 폼 컴포넌트 — UI 분기
- `categories.config.form_schema` JSON으로 폼 정의 → 자동 렌더 (이상)
- 또는 카테고리별 컴포넌트 매핑 (현실)

```jsx
// PWA 카테고리별 폼 컴포넌트 매핑
const CATEGORY_FORMS = {
  aircon: AirconExtraForm,    // (없거나 가전 다중선택)
  vacuum: VacuumExtraForm,    // 모델명 입력
  marble: MarbleExtraForm,    // 면적 + 공간 + 옵션
  doorlock: DoorlockExtraForm,
};
const Extra = CATEGORY_FORMS[category.code] ?? null;

// 공통 폼
<CommonTaskForm task={task} />
{/* 카테고리 추가 필드 */}
{Extra && <Extra task={task} />}
```

→ 카테고리 추가 = **컴포넌트 1개 추가** (없으면 0)

## 새 카테고리 추가 매뉴얼 (이상적 워크플로)

도어락 카테고리를 추가한다고 가정.

### Step 1 — DB 데이터 추가 (코드 변경 0)

```sql
-- 1. 카테고리
INSERT INTO categories (code, name, unit, qty_kind, config)
VALUES ('doorlock', '도어락', '대', 'integer',
  '{"pricing_kind":"flat","photo_steps":["after"]}');

-- 2. 서비스 종류
INSERT INTO service_types (category_id, code, name) VALUES
  ((SELECT id FROM categories WHERE code='doorlock'), 'install', '설치'),
  (..., 'replace', '교체'),
  (..., 'repair', '수리');

-- 3. 기종
INSERT INTO appliance_types (category_id, code, name) VALUES
  (..., 'digital', '디지털'),
  (..., 'mechanical', '기계식'),
  (..., 'smart', '스마트');

-- 4. 작업 종류 + 기본 단가
INSERT INTO work_types (service_type_id, appliance_type_id, code, name, default_unit_price)
VALUES (..., 'digital_install', '디지털 도어락 설치', 80000);
-- ... 모든 조합

-- 5. 회사별 단가 오버라이드 (선택)
INSERT INTO pricing_rules (tenant_id, work_type_id, unit_price, travel_fee)
VALUES ((SELECT id FROM tenants WHERE slug='allit'), ..., 80000, 30000);

-- 6. 회사가 도어락 카테고리 활성화
INSERT INTO tenant_categories (tenant_id, category_id) VALUES (..., ...);
```

### Step 2 — UI 자동 노출 확인

PWA를 새로 빌드 X. 다음이 자동:
- 신규 접수 화면 → 카테고리 선택 드롭다운에 "도어락" 추가
- 작업 종류 선택 → 도어락 종류 자동 노출
- 가격 표시 → flat 모델로 자동 계산
- 사진 화면 → 1단계 (after만) 자동 표시

### Step 3 — (필요 시) 폼 컴포넌트 추가

도어락에 "도어 종류 (이중/단일)" 같은 특수 입력이 필요하면:

```jsx
// src/categories/doorlock/DoorlockExtraForm.jsx
export default function DoorlockExtraForm({ task, onChange }) {
  return (
    <Field label="도어 종류" ...>
      <select value={task.category_data?.door_type ?? ''} onChange={...}>
        <option value="single">단일</option>
        <option value="double">이중</option>
      </select>
    </Field>
  );
}
```

```jsx
// src/components/CategoryForms.jsx
import DoorlockExtraForm from "../categories/doorlock/DoorlockExtraForm.jsx";
const CATEGORY_FORMS = {
  ...,
  doorlock: DoorlockExtraForm,
};
```

→ **변경 라인 수**: 컴포넌트 1개 + 매핑 1줄 = ~30줄

### Step 4 — (필요 시) 가격 함수 분기 추가

flat 모델은 이미 공통 함수에 있음. 새 모델 (예: "층수별 단가")이 필요할 때만:

```js
// src/lib/pricing.js
export function computeEstimate(category, items, options) {
  switch (category.config.pricing_kind) {
    case 'unit_price_table': return _unitPriceTable(items);
    case 'area_x_rate':       return _areaXRate(items, options);
    case 'flat':              return _flat(items, options);
    case 'floor_based':       return _floorBased(items, options); // ← 추가
    default: return 0;
  }
}
```

→ **변경 라인 수**: 1 case 추가 (~5줄)

## 매뉴얼 요약 — 카테고리 추가 비용

| 추가 항목 | 추가 위치 | 코드 변경 | 데이터 변경 |
|---|---|---|---|
| 새 카테고리 (필드 동일) | `categories` + `service_types` + `appliance_types` + `work_types` + `pricing_rules` | **0** | 5 테이블 INSERT |
| 카테고리 + 새 폼 필드 | + `tasks.category_data` JSONB 사용 + 폼 컴포넌트 1개 | **30줄** | 동일 |
| 카테고리 + 새 가격 모델 | + `pricing.js` 함수 분기 1 case | **5줄** | 동일 |
| 카테고리 + 새 기사 자격 시스템 | + `work_types.required_cert` 사용 (이미 컬럼 있음) | **0** | 동일 |
| 카테고리 + 새 사진 단계 | + `categories.config.photo_steps` JSON | **0** | 동일 |

**최악의 경우**: 새 카테고리 + 새 폼 + 새 가격 모델 = **약 35줄 코드 + 5 테이블 INSERT**.

## 회사별 카테고리 활성화 (옵션)

```sql
CREATE TABLE tenant_categories (
  tenant_id   uuid REFERENCES tenants(id),
  category_id uuid REFERENCES categories(id),
  active      boolean DEFAULT true,
  PRIMARY KEY (tenant_id, category_id)
);
```

- 쿨가이 = 에어컨만
- 종합 회사 = 에어컨 + 청소기 + 도어락
- UI는 `tenant_categories.active=true`인 카테고리만 노출

## 카테고리 간 공통화 가능 영역

새 카테고리 추가 비용을 더 낮추기 위해 공통화할 것들:

### 1. 폼 schema-driven 렌더 (선택 사항, 고급)

`categories.config.form_schema` JSONB로 폼 정의 → 자동 렌더:

```json
{
  "fields": [
    { "name": "model_name", "type": "text", "label": "모델명" },
    { "name": "area", "type": "decimal", "label": "면적(㎡)", "min": 0 },
    { "name": "room_type", "type": "select",
      "label": "공간",
      "options": [
        { "value": "kitchen", "label": "주방" },
        { "value": "bath", "label": "욕실" }
      ]
    }
  ]
}
```

PWA `<DynamicForm schema={category.config.form_schema} />` 컴포넌트 1개로 모든 카테고리 폼 자동 렌더.

→ **장점**: 새 카테고리 = 데이터만으로 폼까지 끝
→ **단점**: 복잡한 검증/조건부 필드 표현 어려움 (한계 있음)

**권장**: MVP에서는 컴포넌트 매핑(간단), N카테고리 안정화 후 schema-driven 도입 검토.

### 2. 가격 모델 플러그인

`computeEstimate` 함수를 인터페이스화 → 카테고리 패키지에서 export:

```js
// src/categories/aircon/pricing.js
export const pricingKind = 'unit_price_table';
export function compute(items) { ... }

// src/lib/pricing.js
import * as aircon from '../categories/aircon/pricing.js';
import * as marble from '../categories/marble/pricing.js';
const PRICERS = { aircon, marble, ... };
export function computeEstimate(category, items, options) {
  return PRICERS[category.code].compute(items, options);
}
```

→ 새 카테고리 = `src/categories/<code>/pricing.js` 1 파일 추가

## 안티패턴 (피할 것)

❌ **카테고리별 if/else 폭발**
```js
if (task.category === 'aircon') { ... }
else if (task.category === 'marble') { ... }
else if (task.category === 'doorlock') { ... }
```
→ 카테고리 추가마다 N곳 수정. 의존 매핑 패턴으로 전환.

❌ **카테고리별 테이블 분리**
- `aircon_tasks`, `marble_tasks`, `doorlock_tasks` … 분리
→ 카테고리 추가마다 테이블 추가. 한 컬럼(category_id)으로 그릇 통일.

❌ **하드코딩된 enum**
```ts
type Category = 'aircon' | 'marble' | 'doorlock';
```
→ TypeScript 자동완성에는 좋지만, 런타임 데이터 추가가 코드 수정으로 이어짐. 배포 후 카테고리 추가가 안 됨.
