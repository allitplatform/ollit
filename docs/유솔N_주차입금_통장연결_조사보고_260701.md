## [1] 현재 유솔 주차 입금 처리 흐름 (코드 근거)

### 데이터 모델

#### `principal_weekly_remittances` 테이블 (Mig 059)
```
PK: id (uuid)
UNIQUE: (principal_id, week_start)
컬럼:
  tenant_id        — 11111111-...
  principal_id     — usol_n / usol_h (P003 통합계정)
  week_start       — 그 주 월요일 (KST date)
  week_end         — 그 주 일요일 (KST date)
  remitted_amount  — int (회사 실수령액 ★)
  remitted_at      — 원청 보고 시각
  remitted_by      — 원청 사용자 id
  confirmed_at     — 회사 확인 시각 (NULL = 미확인)
  confirmed_by     — 운영자 id
  note             — 자유 메모
```

#### `task_items.company_received_at` (Mig 038)
- 별도 컬럼. **주차 입금 워크플로와 분리됨** (FK도, 트리거도 없음).
- 다른 화면(CSV 매칭 / 정산판)에서 `markTaskItemsField('company_received_at')` 일괄 마킹.
- 즉 정산판 카운트와 주차 confirm은 직접 연동 안 됨 (운영자가 따로 처리).

### 흐름 3단계 (RPC 호출)

| # | 주체 | 화면 | 호출 | 효과 |
|---|---|---|---|---|
| 1 | 원청 (P003 partner) | `PrincipalSettleTab` 측 "입금했습니다" | `markPrincipalRemitted(p_user_id, p_principal_id, p_week_start, p_week_end, p_amount, p_note?)` | `principal_weekly_remittances` UPSERT — `confirmed_at IS NULL`일 때만 |
| 2 | 회사 (admin/operator) | `UsolNTracking` 또는 `UsolNToCompanySection` 측 "회사 입금 확인" | `confirmPrincipalRemit({ remitId })` → `confirm_principal_remittance(p_user_id, p_id)` | `confirmed_at = now()`, `confirmed_by = p_user_id`. **★ cashflow row 생성 안 함 — 이게 root cause** |
| 3 | (확인 전) 원청 | "보고 취소" | `undo_principal_remit(p_user_id, p_id)` | `confirmed_at IS NULL`일 때만 DELETE. **confirmed 된 row는 변경 불가** |

### 핵심 — `remitted_amount`에 무엇이 들어가나

**`PrincipalSettleTab.jsx:430-431`** — 보고 시 계산:
```js
// 회사 입금액 = ROUND(net_amount × 0.85). net_amount NULL → 0.
slot.sum += companyAmountOf(it);
```

→ **`remitted_amount` = SUM(ROUND(task_items.net_amount × 0.85))**
   = **회사 실수령액** (유솔 수수료 15% 차감 후)
   = 사장님 화면의 "11,879,718원" 그 자체.

✅ **통장 IN에 그대로 쓰면 됨**. 변환 산식 추가 X.

(헤더 코멘트의 "subtotal 합 스냅샷"은 컬럼 코멘트 시점 옛 설명. 실제 클라가 넘기는 값은 회사 실수령액. 코드가 진실 소스.)

## [2] 통장 연결 설계

### 핵심 발견: confirm RPC가 cashflow 미생성
`Mig 060/061/063` 어디에도 `confirm_principal_remittance` 본문에 cashflow INSERT 없음. 즉 **현재 운영의 누락분은 모두 이 함수가 cashflow row를 만들지 않는 게 원인**. 어제 11,879,718도 동일.

### 신규 RPC 1개 (Mig 160 가칭) — Mig 156 대칭

```sql
confirm_principal_remit_with_cashflow(
  p_id    uuid,            -- principal_weekly_remittances.id
  p_actor uuid             -- 운영자 user_id (p_user_id 패턴 동기)
) RETURNS jsonb
```

처리 순서 (원자 트랜잭션, SECURITY DEFINER):

1. **권한** — `_caller_is_admin(p_actor)` (owner/admin/operator)
2. **row 로드 + 가드** — `FOR UPDATE`:
   - 없으면 `{ ok:false, error:'not_found' }`
   - `confirmed_at IS NOT NULL` → `{ ok:false, error:'already_confirmed' }` (멱등)
   - `remitted_amount <= 0` → confirmed_at만 채우고 cashflow skip (zero-remit 케이스)
3. **confirmed_at 채우기** — `confirmed_at = now()`, `confirmed_by = p_actor`
4. **memo 생성** — `principals.name` (또는 code) + week_start 사용:
   ```
   '유솔N 주차정산 · 2026-06-22 ~ 2026-06-28'
   ```
   또는 사장님 선호 "6월 4주차" 형식:
   ```
   to_char(week_start, 'FMMM') || '월 ' ||
   to_char(week_start, 'FMW') || '주차'
   ```
   (`FMW`는 그 달의 N번째 주 — PostgreSQL 표준. ISO 주차 아님)
5. **cashflow INSERT** — Mig 156 패턴:
   ```
   tenant_id   = '11111111-...'
   direction   = 'in'
   amount      = remitted_amount
   flow_date   = (now() AT TIME ZONE 'Asia/Seoul')::date
   memo        = 위 산출
   created_by  = p_actor
   source      = 'auto_usoln_remit'      ★ 기사용 'auto_engineer_remit'과 분리
   source_ref  = p_id                     ★ principal_weekly_remittances.id
   ON CONFLICT (source, source_ref) WHERE source IS NOT NULL DO NOTHING
   ```
6. **결과 반환** — `{ ok, remit_id, cashflow_inserted, amount, memo }`

### 신규 RPC 2개 (선택) — 취소 경로

기사 입금엔 `cancel_confirm_engineer_remit_with_cashflow`(Mig 156) 있음. 유솔에도 대칭 필요한가?

**현재 유솔 운영 패턴 (코드상)**: 한번 confirmed된 row는 변경/삭제 불가 (`undo_principal_remit`는 `confirmed_at IS NULL` 시에만 작동).

**두 가지 안**:

| 안 | 설명 | 장단점 |
|---|---|---|
| **A. confirm-only** | unconfirm 경로 없음 — 현재 워크플로 그대로 유지. 통장 IN만 추가. | 단순. 실수로 confirm 시 DB 직접 정정 필요. |
| **B. confirm + unconfirm 양쪽** | 신규 `cancel_confirm_principal_remit_with_cashflow(p_id, p_actor)` 추가: `confirmed_at NULL` 복귀 + 해당 cashflow row DELETE. | 기사 패턴 동기. 운영자가 잘못 confirm한 경우 복구 가능. RPC 1개 더 추가. |

**권장**: **B안**. 실수 복구 안전망 + 기사 입금 패턴과 동기. RPC 1개 추가 부담 작음.

### 멱등성 / 충돌 가드

- `confirm_principal_remit_with_cashflow` 재호출:
  - `confirmed_at IS NOT NULL` 가드 → 두 번째 호출은 `already_confirmed` 반환, cashflow row 변경 X
  - 추가 안전망: `ON CONFLICT (source, source_ref) DO NOTHING` (Mig 156 partial UNIQUE 활용)
- `cancel_confirm_principal_remit_with_cashflow` 재호출:
  - 첫 호출: confirmed_at NULL + cashflow DELETE
  - 두 번째: 이미 NULL → `{ ok:false, error:'not_confirmed' }`

## [3] 과거 주차 소급 + 어제 11,879,718 처리

### 과거 주차 (5월 ~ 6월 3주차 이전)

- `principal_weekly_remittances` 전체 SELECT 시 `confirmed_at NOT NULL` row가 다수 존재 (운영자가 매주 확인 처리해왔음)
- 가계부 baseline (사장님 spec 19,700,106원)이 어느 시점에 산정됐는지가 결정 포인트:

| 시나리오 | 처리 |
|---|---|
| baseline 시점 이전 confirmed 분이 baseline에 반영됨 | **소급 금지** — 통장에 또 넣으면 이중 계상 |
| baseline 시점 이후 confirmed 분 (= 어제 11,879,718 같은 케이스) | 통장 수동 INSERT 1건 (사장님 통장 화면에서 직접) — 또는 별도 backfill SQL |

→ Mig 156 패턴 그대로: **과거분 소급 금지가 안전 디폴트**. 사장님이 baseline 시점을 명확히 알고 그 이후 confirmed 건이 몇 개인지 정확히 알 때만 수동 INSERT.

### 어제 11,879,718 — 처리 옵션

**옵션 1 (권장)** — 사장님이 PC 통장 화면에서 수동 입금 추가:
- 날짜: 어제 (확인일 KST)
- 금액: 11,879,718
- 메모: `유솔N 주차정산 · 6월 4주차 (Mig 160 적용 전 누락분)`
- 단점: source NULL이라 자동 멱등성 가드와 무관 — 나중에 같은 주차를 RPC가 또 처리할 위험 X (RPC는 신규 호출만 INSERT, 어제 row는 이미 confirmed_at NOT NULL → already_confirmed 반환)

**옵션 2** — backfill SQL 1줄 (Mig 160의 verify 섹션에 옵션으로):
```sql
-- 어제 1건만 정정 (사장님 OK 후)
INSERT INTO bookkeeping_cashflow (
  tenant_id, direction, amount, flow_date, memo,
  created_by, source, source_ref
)
SELECT
  tenant_id, 'in', remitted_amount,
  (confirmed_at AT TIME ZONE 'Asia/Seoul')::date,
  '유솔N 주차정산 · backfill ' || week_start::text || ' ~ ' || week_end::text,
  confirmed_by, 'auto_usoln_remit', id
FROM principal_weekly_remittances
WHERE id = '<어제 row uuid>'
  AND confirmed_at IS NOT NULL
ON CONFLICT (source, source_ref) WHERE source IS NOT NULL DO NOTHING;
```

→ **옵션 1이 더 안전**. backfill SQL은 baseline 산정 시점 확정 후 별도 라운드에서 결정.

## [4] 리스크

| 위험 | 정도 | 처치 |
|---|---|---|
| **과거 confirmed 행 이중 계상** | 🔴 High | 소급 금지가 디폴트. baseline 시점 확정 전 backfill 절대 X |
| **`remitted_amount`가 sub_total인지 회사 실수령인지 헷갈림** | 🟢 Low | 코드 근거 확인됨 — `companyAmountOf(it)` = ROUND(net × 0.85) = 회사 실수령 |
| **source 충돌 (기사 cashflow와 섞임)** | 🟢 Low | `source='auto_usoln_remit'` 별도. partial UNIQUE는 `(source, source_ref)` 조합이라 기사용과 자연스럽게 분리 |
| **week_start 키 변경 / 보고 amount 수정** | 🟡 Med | confirmed_at 채워진 row는 `mark_principal_remitted`가 UPSERT 거부 (`WHERE confirmed_at IS NULL`) → 안전. 단 confirmed 전 단계에서 amount 바뀌면 confirm 시점 amount로 cashflow IN — 정상 |
| **통합계정 P003 (usol_h + usol_n) row 두 개** | 🟡 Med | RPC가 row 단위(`p_id`)라 각 row별 cashflow 1건. usol_h와 usol_n 모두 자동 IN됨 — 사장님이 둘 다 원하는지 확인 필요 (지금은 usol_n만 운영 중이라 사실상 무관) |
| **principal_weekly_remittances.confirmed_at가 backfill로 채워진 경우** | 🟡 Med | 옛 운영 정정 SQL이 직접 UPDATE한 row 있을 가능성. RPC는 신규 호출만 INSERT라 영향 X |
| **memo의 "N월 N주차" 산출** | 🟢 Low | `to_char(week_start, 'FMMM')` + `FMW` — PostgreSQL 표준. 검증은 사장님이 현재 화면 표시와 대조 |

## 산출물

1. **흐름 코드 근거**:
   - `Mig 059` (table) + `Mig 060/061/063` (RPCs)
   - `principalRemitDb.js:79-97` (mark) / `:142-155` (confirm) / `:99-112` (undo)
   - `PrincipalSettleTab.jsx:420-458` (amount 산식 = ROUND(net × 0.85) = 회사 실수령)
   - `UsolNTracking.jsx:120-135` (회사측 confirm 호출처)
   - **confirm RPC가 cashflow row 미생성** = root cause

2. **통장 연결 설계**:
   - 신규 RPC `confirm_principal_remit_with_cashflow(p_id, p_actor)` — confirm + cashflow IN 원자
   - `source='auto_usoln_remit'` / `source_ref=remit.id`
   - amount = `remitted_amount` 그대로 (이미 회사 실수령액)
   - memo = `'유솔N 주차정산 · {N월 N주차}'` or `'... {week_start} ~ {week_end}'`
   - flow_date = 확인일 KST
   - 선택 RPC `cancel_confirm_principal_remit_with_cashflow` (B안 권장) — unconfirm + cashflow DELETE

3. **소급**: 과거 confirmed 분은 baseline 반영 가정 — **소급 금지**. 어제 1건만 사장님이 통장에서 수동 입금 추가가 가장 안전.

4. **리스크**: baseline 이중 계상 / 통합계정 row 분리 / memo 주차 표기
