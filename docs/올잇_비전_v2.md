# 올잇 비전 v2 — Multi-Tenant Multi-Category 홈서비스 플랫폼

**작성일**: 2026-04-30
**상태**: 초안 v2 (사장님 의지 반영, 세부 검토 대기)
**v1 대비 변경**:
- 1회사 (쿨가이) → **N회사** (Multi-Tenant SaaS)
- 1카테고리 (에어컨) → **N카테고리** (홈서비스 전반)

## 한 문장

> "홈서비스 회사라면 누구나 가입해서 자기 회사 작업을 통합으로 관리할 수 있는 SaaS"

지금: 사장님 본인 회사 (올잇 = 에어컨 청소).
향후: 다른 홈서비스 회사도 입주.

## 4가지 핵심 원칙

### 원칙 1 — Multi-Tenant SaaS (회사별 격리)

- N개 홈서비스 회사가 한 시스템에 입주 (각 회사 = `tenant`)
- 회사 A의 데이터는 회사 B가 절대 못 봄 (DB 수준 격리)
- 각 회사 = 자기 기사/원청/고객/작업만 관리
- 운영팀(올잇)은 모든 tenant를 모니터링 가능 (super-admin)

**왜 중요한가**: 처음부터 멀티테넌트로 안 짜면 두 번째 회사 들어오는 순간 거의 처음부터 다시 만들어야 함. tenant_id 컬럼 한 줄 추가는 간단해 보이지만 이미 깔린 인덱스/조회/UI가 다 single-tenant 가정이면 손볼 곳이 폭발.

### 원칙 2 — Multi-Category (홈서비스 전 영역)

- **에어컨** (현재 진행 중)
- **청소기**, **대리석**, **도어락**, **방충망**, **세탁기**, **냉장고**, ...
- 정해진 건 아니고 큰 방향. 카테고리 추가는 plug-in 방식
- 회사마다 다룰 카테고리 다름:
  - 에어컨 전문 회사 (현재 사장님)
  - 에어컨+청소기 회사
  - 종합 홈서비스 회사

**왜 중요한가**: 카테고리가 늘어날 때 코드/스키마를 매번 바꾸지 않게. 이상은 **새 카테고리 = 데이터 추가만**.

### 원칙 3 — 외부 의존 0 (통합형)

- Google Sheets 의존 **버림** (지금은 시뮬 단계라 쓰는 것뿐)
- 자체 DB로 통합 (Supabase 채택 검토 — 별도 문서)
- 카카오톡/문자/이메일/알림 = 외부 *연동*이지만 **데이터 주권은 우리**
- 시트는 회사가 export 받아 보는 **보조 수단**으로 격하

**왜 중요한가**:
- 시트는 1회사 1단일소스 모델에 적합. N회사 N카테고리에선 시트 수가 폭발.
- 시트 동시쓰기 락, 50000 row 제한, GAS 6분 실행 제한 등 SaaS급 운영에 부적합.
- 외부 시스템(Google) 정책 변동에 사업이 종속됨.

### 원칙 4 — 카테고리별 커스텀 (그릇은 같고 소스는 다름)

> **그릇** (시스템 공통): tenant / user / task / schedule / payment / photo / 알림 등 — 카테고리 무관
> **소스** (카테고리별): 작업 종류 / 가격 모델 / 기사 자격 / 사진 요구사항 / 폼 필드 — 카테고리에 따라 변형

처음부터 그릇을 크게 만들어 두면 새 카테고리 = 소스 추가만으로 끝남.

---

## "그릇과 소스" 비유 더 자세히

### 그릇 (공통 뼈대) — 카테고리에 무관

| 그릇 요소 | 무엇을 담음 | 카테고리 영향 |
|---|---|---|
| 회사 (tenant) | 입주 회사 정보 | 없음 |
| 사용자 (user) | 운영자/원청/기사/관리자 | 없음 |
| 작업 (task) | 한 건의 서비스 요청 | 카테고리 ID로 분류만 |
| 일정 (schedule) | 작업 일시 + 기사 배정 | 없음 |
| 결제 (payment) | 고객 결제 + 정산 | 가격 모델은 카테고리별 |
| 사진 (photo) | before/after/단계별 | 단계 정의는 카테고리별 |
| 메시지/알림 | 카톡/문자/이메일 발송 로그 | 템플릿은 카테고리별 |

### 소스 (카테고리별 변형) — 같은 그릇에 다른 내용

| 카테고리 | 단위 | 가격 모델 | 기사 자격 | 사진 단계 | 폼 특이사항 |
|---|---|---|---|---|---|
| 에어컨 | 대 | 기종×작업 단가표 | 냉매 자격증 (충전만) | before/after | 가전 종류 + 수량 |
| 청소기 | 대 | 기종별 정액 | 가전 기본 | before/after | 모델명 (호환 부품) |
| 대리석 | ㎡ | 면적×단가+옵션 | 시공 기능사 | 시공 전/중/후 (3단계) | 면적 입력 |
| 도어락 | 대 | 기종 정액 + 출장비 | 잠금장치 자격? | 설치 후 1장 | 도어 종류, 비밀번호 정책 |

## 단계별 진화 로드맵

```
[v1] 시뮬 (1회사, 1카테고리)        ← 어제까지
  PWA + 메모리만 + 사진 mock
       ↓
[v2 비전 정립] 지금                  ← 오늘
  멀티테넌트/멀티카테고리 그릇 설계
       ↓
[v3] MVP (1회사, 1카테고리, 진짜 백엔드)
  Supabase + tenant=쿨가이 + category=에어컨
  → 김쿨가이 대표 시범 운영
       ↓
[v4] 멀티 카테고리 (1회사 N카테고리)
  쿨가이가 청소기 추가
       ↓
[v5] 멀티 회사 (N회사 N카테고리)
  외부 회사 1-2곳 입주
       ↓
[vN] 운영 SaaS
```

### 큰 결정 (사장님 검토)

**결정 V1 — 시뮬 GAS 결선을 마무리할지, 바로 Supabase로 점프할지**

| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 시뮬 GAS 결선 마무리 (8-A 끝까지) → 안정화 → Supabase로 마이그레이션 | 점진적, 학습 비용 분산 | 시뮬 GAS 작업 일부 throwaway |
| B | 8-A 여기서 멈춤 → 바로 Supabase 도입 (v3 MVP 직진) | 두 번 일 회피 | Supabase 학습 + 설계 부담 즉시 |
| C | 시뮬 GAS는 PWA 검증용 그대로 두고, Supabase는 별도 트랙으로 병행 | 양쪽 학습 | 자원 분산 |

**추천**: **B (바로 Supabase)** — v2 비전이 GAS+Sheets와 정면 충돌. 시뮬 GAS 결선을 마쳐도 Supabase 가면 다 새로 짜야 함. 다만 v3 MVP 진입 전 설계가 충분히 단단해야 함 → Supabase 아키텍처 문서 + 카테고리 확장 설계 문서 먼저 검토 후 결정.

## 사장님 의지 (원문 인용 — 비전 v2 근거)

```
지금은 에어컨 청소만 하지만, 나중에 카테고리 확장 예정:
- 청소기 청소
- 대리석 시공/관리
- 도어락 / 방충망 / 등등 홈서비스 다 (정해진 건 아니고 큰 방향)

그래서 시스템을 "그릇"처럼 만들고 싶어.
카테고리는 "소스"고 나중에 하나씩 추가.
그릇이 작으면 소스 추가할 때마다 다시 만들어야 하니까,
처음부터 큰 그릇으로.
```

이 문장이 v2의 모든 결정의 근거.
