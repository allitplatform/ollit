## [1] 취소→완료 복구

### 1-1. 현재 취소가 일으키는 것 (코드 근거)

#### partner_full_cancel / admin_full_cancel (Mig 074, `db/migrations/074_cancel_rpcs_p_actor.sql:95-266`)

```
1) UPDATE tasks SET
     status = '취소',
     category_data ||= jsonb_build_object(
       'cancelReason', 'previousStatus' = OLD.status, 'cancelActor',
       'cancelActorUserId', 'cancelAt', 'wasCompleted'
     ),
     cancel_engineer_comp_kind   = 'none',
     cancel_engineer_comp_amount = 0
2) UPDATE task_items SET is_canceled = true, canceled_reason, canceled_at = now()
   WHERE NOT is_canceled
```

#### 연쇄 트리거 (자동)

- **task_items_partial_sync_before_trg** (Mig 070, BEFORE UPDATE)
  - `is_canceled` false → true 전환 시:
    - `metadata._pre_cancel_paid = customer_paid_amount`
    - `metadata._pre_cancel_net = net_amount`
    - `customer_paid_amount = 0` / `net_amount = 0` 강제
- **task_items.subtotal** (Mig 070, GENERATED STORED)
  - `CASE WHEN is_canceled THEN 0 ELSE qty × unit_price END`
  - **qty / unit_price는 무손상 보존** ← 복구의 진실 소스
- **task_items_resync_task_total_trg** (Mig 070, AFTER)
  - `tasks.product_price = SUM(미취소 subtotal)` 재합산
  - 가드: 새 합계 ≠ 옛 값일 때만 UPDATE → 트리거 체인 차단
- **task_items_compute_trg** (Mig 028, AFTER)
  - `compute_payment(task_id)` 호출
- **compute_payment v20** (Mig 139)
  - `v_canceled_active := (status='취소' AND cancel_engineer_comp_kind IS NOT NULL)`
  - true → engineer = comp_amount, principal = 0, owner = -engineer
  - false → 정상 분배 계산

### 1-2. 원본 금액(80,000) 어디서 살아남나

A-260628-006 / item_id `8c4cbd0e-af05-4ce7-b0a4-b975fa083a7f` 기준:

| 컬럼 | 취소 후 상태 | 복구 시 소스 |
|---|---|---|
| `task_items.qty` | 1 (보존) | ← 그대로 |
| `task_items.unit_price` | 80,000 (보존) | ← 그대로 |
| `task_items.subtotal` | 0 (GENERATED) | qty × unit_price 자동 재계산 |
| `task_items.customer_paid_amount` | 0 | `metadata._pre_cancel_paid` 백업값 |
| `task_items.net_amount` | 0 | `metadata._pre_cancel_net` 백업값 |
| `tasks.product_price` | 0 (resync) | SUM(미취소 subtotal) 자동 재합산 |
| `payments.engineer_amount` | 0 또는 30,000(visit_fee) | compute_payment 재호출 |

**결론**: 원본 80,000 = `task_items.qty × unit_price` (DB 영구 보존). category_data까지 안 봐도 됨.

화면 "₩80,000 취소선" UI도 같은 소스 — 견적표시는 `unit_price × qty` 기준이지 subtotal 기준이 아님 (확인 필요하나 자연스러운 가정).

### 1-3. 복구 RPC 설계 — `admin_restore_canceled_task`

```sql
admin_restore_canceled_task(
  p_task_id  uuid,
  p_actor    uuid,                       -- 운영자 user_id
  p_to_status text DEFAULT NULL          -- NULL이면 category_data.previousStatus 사용
)
RETURNS jsonb
```

**처리 순서 (RPC 본문, 원자 트랜잭션)**:

1. 권한 가드 — `_caller_is_admin(p_actor)`
2. task 조회 — `status = '취소'` 검증, 아니면 거부
3. 복귀 target 결정
   - `p_to_status` 우선
   - 없으면 `category_data->>'previousStatus'`
   - 없으면 `category_data->>'wasCompleted' = 'true'` → '완료', 아니면 '확정'
   - allowed set: `{완료, 확정, 진행, 배정}`
4. **task_items 복귀** (먼저)
   ```sql
   UPDATE task_items SET
     is_canceled = false,
     canceled_reason = NULL,
     canceled_at = NULL
   WHERE task_id = p_task_id AND is_canceled = true;
   ```
   - BEFORE trigger가 `customer_paid_amount` / `net_amount` 백업값 자동 복원
   - subtotal GENERATED가 80,000 복귀
   - AFTER resync trigger가 `tasks.product_price` 재합산
   - AFTER compute trigger가 `compute_payment` 호출 (status='취소' + comp_kind='none' → visit_fee=0 분기)
5. **tasks 복귀** (그 다음)
   ```sql
   UPDATE tasks SET
     status = v_target_status,           -- '완료' 등
     cancel_engineer_comp_kind = NULL,
     cancel_engineer_comp_amount = NULL,
     category_data = (category_data
       - 'cancelReason'
       - 'cancelActor'
       - 'cancelActorUserId'
       - 'cancelActorPrincipalCode'
       - 'cancelAt'
       - 'previousStatus'
       - 'wasCompleted')
       || jsonb_build_object(
         'restoredAt', now() UTC ISO,
         'restoredBy', p_actor,
         'restoredFromCancel', true
       ),
     completed_at = CASE
       WHEN v_target_status = '완료' AND completed_at IS NULL THEN COALESCE(scheduled_at, now())
       ELSE completed_at
     END,
     updated_at = now()
   WHERE id = p_task_id;
   ```
   - `sync_task_items_trg`는 `UPDATE OF category_data, product_price`에만 발화. status / cancel_* / completed_at만 바꿨다 해도 category_data가 같이 변경되므로 **발화함**
   - **🚨 위험**: depth=1 → DELETE+INSERT task_items → is_canceled 플래그 + customer_paid_amount 등 모두 소실
6. **명시적 compute_payment 재호출** — task_items_compute_trg가 위에서 한 번 돌았지만 status 바꾼 후 안전하게 한 번 더
7. status_history INSERT
8. 결과 jsonb 반환

#### 🚨 sync_task_items_trg 충돌 처리 (필수)

**현재 상태** (Mig 017 → 069 → 086 → 093, 069b 미적용):
- 트리거 발화 조건: `UPDATE OF category_data, product_price ON tasks`
- 본문: `pg_trigger_depth() > 1` 가드만 있음 (086), 069b의 `IS NOT DISTINCT FROM workItems` 가드 **없음**
- depth=1 진입 → 무조건 task_items DELETE → workItems 있으면 재INSERT (is_canceled / received_amount / order_type 일부 / metadata 모두 소실)

**해결 옵션 3가지**:

**A. category_data를 안 건드린다** (가장 안전)
- 5번 UPDATE에서 `category_data` 컬럼은 그대로 두고, status / cancel_* / completed_at만 변경
- 메모리얼 흔적은 `restoredAt` 등을 cancel* 키 옆에 같이 두기 → 키 충돌 없음 (cancel* 그대로 남겨두면 history로 유용)
- 하지만 `cancel_engineer_comp_kind = NULL` 만 바꿔도 status 안 바꾸면 compute_payment_trg는 발화 X. 그래서 status / cancel_* / completed_at 묶음 UPDATE는 OK
- `sync_task_items_trg`가 `UPDATE OF category_data, product_price`에만 발화하므로 category_data 안 건드리면 **트리거 미발화** ✓

**B. 가드를 먼저 강화** (069b 재적용)
- 069b의 `IS NOT DISTINCT FROM workItems` 본문을 Mig 157(가칭)으로 재적용
- 그 후에 복구 RPC 만들면 category_data를 자유롭게 바꿔도 안전
- 부가 효과: 향후 모든 흐름에서 일관된 안전성

**C. RPC 내부에서 ALTER TABLE DISABLE TRIGGER** — 권장 안 함 (race condition, security 위험)

**권장**: **A + B 조합**. 1차 릴리스는 A로 진행(category_data MERGE 안 함, cancel* 키는 잔존 → "복구됨" 표시는 별도 컬럼/플래그). 후속으로 B 가드 강화하면 마음 편함.

### 1-4. 역행 가드 충돌

- 클라이언트 측 FINALIZED set (`AdminApp.jsx:1820`)에 '취소' 포함 → 일반 수정 차단
- 복구 RPC는 서버 측 SECURITY DEFINER이라 클라이언트 가드 우회. 클라이언트는 **"복구 버튼"이라는 명시적 진입로**만 제공하면 됨 (일반 status 변경 흐름과 분리)
- 다른 역행 (완료→배정 등)은 클라이언트 가드 그대로 유지. 복구 RPC는 **'취소' status에서만 호출 허용** (RPC 본문에서 검증)

## [2] 냉매 분배 엔진

### 2-1. 현재 계산 흐름 (`compute_payment` v20, Mig 139)

#### loop 내 (item별)
```
v_calc_result = calculate_commission(principal, 'refrigerant', appliance, unit_price)
  → KA refri 스탠드: principal = 견적 × 0.35
                     engineer  = total / 2 (정책 기본)
                     calc_method = '비율_견적금액'

IF service = 'refrigerant' AND assigned_engineer_id NOT NULL:
  v_engineer_rate = COALESCE(users.refrigerant_rate, 50)
  IF rate >= 100: v_eng = total - principal  (회사 0)
  -- rate < 100: loop 내 v_eng 미수정 (task-level override가 정정)
```

#### loop 후 (task-level override, v19+v20)
```
IF pure_refrigerant AND assigned NOT NULL:
  IF rate >= 100:
    v_total_engineer = product + extra - principal + travel  (v20 추가)
  ELSE:
    v_total_engineer = FLOOR((product + extra) × rate / 100) + travel
```

### 2-2. 시뮬레이션 — 사장님 정책 vs 엔진 결과

#### 케이스 ①: 구현서 E002, KA 냉매 100,000 (rate=100 기대)

| 단계 | 값 |
|---|---|
| calculate_commission (KA refri 스탠드, 100,000) | principal=35,000 / engineer=50,000 / total=100,000 |
| loop refrigerant 분기 (rate≥100) | v_eng = 100,000 − 35,000 = 65,000 |
| loop 후 override (rate≥100) | v_total_engineer = 100,000 + 0 − 35,000 + 0 = **65,000** ✓ |
| 최종 | engineer=**65,000** / principal=**35,000** / owner=**0** ✓ |

**= 사장님 정책 일치**. 엔진 v20은 rate=100을 정확히 처리.

#### 케이스 ②: 임종일 E018, KA 냉매 80,000 (rate=60 기대)

| 단계 | 값 |
|---|---|
| calculate_commission (KA refri 스탠드, 80,000) | principal=28,000 / engineer=40,000 / total=80,000 |
| loop refrigerant 분기 (rate=60 < 100) | v_eng 미수정 (loop 후 override가 처리) |
| loop 후 override (rate<100) | v_total_engineer = FLOOR(80,000 × 60/100) + 0 = **48,000** ✓ |
| owner | 80,000 − 48,000 − 28,000 = **4,000** ✓ |

**= 사장님 정책 일치**. rate=60도 정확.

### 2-3. 그럼 왜 구현서 건이 50%로 잡혔나? — Root cause 후보

**엔진은 정확합니다.** v20은 rate≥100 / rate<100 양쪽 다 정확히 사장님 정책대로 계산.

따라서 50%로 잡힌 원인은 **users.refrigerant_rate** 값:

| 기사 | 코드 | Mig 050 헤더 기록 | 정책 기대 |
|---|---|---|---|
| 구현서 | E002 | rate=100 (B그룹) | 100 |
| 조동욱 | E022 | rate=100 (B그룹) | 100 |
| 조동석 | A003 | **언급 없음** | 100 (사장님 신규 spec) |

**Mig 050 (2026-05-21)에 조동석 미언급**. 조동석은 50으로 머물러 있을 가능성 큼.
구현서 E002는 Mig 050에서 rate=100 시드 가정이지만 — 실제 DB 값 확인 안 됨 (UPDATE가 Mig 050에 없음, 헤더의 "spec"만 있음).

### 2-4. 진단 SQL (사장님 직접 실행 → 결과 공유)

```sql
SELECT code, name, refrigerant_rate, is_active
FROM users
WHERE code IN ('E002', 'E022', 'A003')
ORDER BY code;
```

**기대**: 3명 모두 100. 50 또는 NULL이면 원인 확정.

### 2-5. 수정 설계

#### Step 1 — users.refrigerant_rate 정정 (SQL 1줄, 사장님 직접 실행)

```sql
BEGIN;
SELECT code, name, refrigerant_rate AS before FROM users WHERE code IN ('E002','E022','A003');

UPDATE users SET refrigerant_rate = 100
WHERE code IN ('E002', 'E022', 'A003')
  AND COALESCE(refrigerant_rate, 50) <> 100;

SELECT code, name, refrigerant_rate AS after FROM users WHERE code IN ('E002','E022','A003');
-- ROLLBACK; / COMMIT; (확인 후)
COMMIT;
```

- "원청별 차등" **필요 없음**. 정책 = 모든 원청에서 대표 3명 = 100%.
- 엔진은 이미 원청별 차등 처리됨 (calculate_commission가 principal별로 다른 principal 계산).

#### Step 2 — 과거 작업 무소급 보장

사장님 요청 "과거 작업 소급 없이 미래만 적용":

- **자연스럽게 미래만 적용됨**. 엔진은 compute_payment 호출 시점의 `users.refrigerant_rate`를 읽음. 과거 payments row는 안 바뀜.
- **단, 오늘 수동 정정한 구현서 2건(379e1fd3 / 4babd82e)은 보호 필요**:
  - 이 2건이 다시 compute_payment 트리거를 타게 되면 (예: task_items 변경, status 변경) 새 rate=100 으로 자동 재계산되어 사장님 손 정정값과 동일하게 65000/35000/0이 나옴 → **결과적으로 무영향**
  - 하지만 더 안전하게 가려면: 사장님이 Mig 실행 직전 두 task의 task_items / tasks를 건드리지 않으면 됨.

#### Step 3 (선택) — 엔진 자체에 "대표 100% 자동" 분기 박지 않음

권장 안 함. 사유:
- 엔진은 ID로 사람 알지 못함. `users.refrigerant_rate` 컬럼이 진실 소스로 깔끔.
- "대표" 개념이 추후 늘어나도 users 테이블 한 줄만 바꾸면 됨.

## [3] 리스크 정리

### 3-1. 취소 복구 — 위험도

| 위험 | 정도 | 처치 |
|---|---|---|
| **sync_task_items_trg DELETE+INSERT** | 🔴 High | 1차: category_data 안 건드림 (옵션 A). 2차: 069b 가드 재적용 (옵션 B) |
| compute_payment 중복 호출 | 🟢 Low | task_items_compute_trg + 명시 호출. idempotent (DELETE + INSERT) → 무해 |
| metadata 백업 누락 (legacy cancel) | 🟡 Med | customer_paid_amount/net_amount=0 잔존 가능. 시각적 확인 + 운영자 수동 보정 안내 |
| `cancel_engineer_comp_kind` NULL 처리 누락 | 🔴 High | RPC가 명시적으로 NULL 세팅 — v_canceled_active 분기 차단 |
| 역행 가드 충돌 | 🟢 Low | RPC 본문에서 status='취소' 검증 후 진행. 클라이언트는 별도 "복구" 버튼만 |
| 송금 이후 복구 시 자금 흐름 | 🔴 High | engineerRemittedAt / engineerRemitConfirmedAt 검증 + 운영자 confirm 다이얼로그 (취소 시 동일 패턴) |

### 3-2. 냉매 엔진 — 위험도

| 위험 | 정도 | 처치 |
|---|---|---|
| 진단 SQL 결과 rate=100이 이미 맞음 | 🟢 Low | 다른 root cause 재조사 (UI editing 흐름 / 캐시) |
| Mig 실행 후 오늘 수동 정정 2건 재계산 트리거 | 🟢 Low | 동일값 (65k/35k/0) 산출. 추가 보호 안 함 권장 |
| 원청별 차등 정책 변경 요구 발생 | 🟢 Low | 본 라운드 spec 외. commission_policies + calculate_commission에 추가 |
| 트리거 순서 / 함수 의존 | 🟢 Low | refrigerant_rate UPDATE는 단순 컬럼 변경. 트리거 영향 0 |

### 3-3. 두 변경의 순서 — 권장

1. **냉매 진단 SQL** (Step 2-4) 먼저 — 5초 소요, 결정 단순화
2. **냉매 정정 UPDATE** (Step 2-5) 결과 보고 후 사장님 OK 시 실행
3. **069b 가드 재적용** (옵션 B, 권장) — 별도 마이그 작성
4. **복구 RPC + UI** — Mig + 클라이언트 동시 작업, 별도 단계
